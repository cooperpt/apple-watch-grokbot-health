# Apple Watch → Grok Bot 健康资料库：睡眠与活动同步说明

## 1. 目标

帮助用户在早上打开微信时，通过 iPhone 快捷指令同步苹果健康数据，让 Grok Bot 给出睡眠与活动的中文小结，并可对比近几天。这里的「实时同步」指打开微信时触发同步。

把每日同步的数据与用户自行提供的历史记录、其他健康资料积累在一起，逐步搭建用户自己的健康资料库。本说明先完成睡眠与活动同步；历史导入和其他资料整合，按用户实际提供的内容另行确认。

## 2. 待完成清单

- 手机端：引导用户授予所需健康数据读取权限，创建快捷指令及「打开微信」自动化。
- 手机端：读取步数、活动能量、HRV、静息心率，以及睡眠阶段和对应时长，发送到用户自己的接收端。
- 服务端：接收数据，按同一晚汇总睡眠阶段，生成中文小结。
- 联调：选健康 App 中某一晚逐项对账，通过后再用于每日同步。

需要用户在手机上操作的环节，给出对应指引；实际完成并收到数据后，再确认搭建成功。

## 3. 权限

批量读取健康样本时，若弹出「共享大量数据」提示，引导用户前往：

**设置 → 快捷指令 → 高级 → 允许共享大量数据。**

## 4. 捷径逻辑

触发条件：打开微信。

读取并发送以下数据：

| 数据 | 处理要求 |
| --- | --- |
| 步数 | 与接收端约定统计时段和单位 |
| 活动能量 | 与接收端约定统计时段和单位 |
| HRV | 保留指标含义和单位，明确取值时段 |
| 静息心率 | 明确取值时段和单位 |
| `sleep_stage_values` | 原始睡眠阶段值列表，不依赖中文名称过滤 |
| `durations` | 对应的时长列表，顺序与阶段值一致，发送前统一并明确单位 |

阶段值和时长必须来自同一批样本，逐条对应；列表长度不一致时先修正，不继续汇总。具体阶段值的含义由读到的实际样本核对，不在此预设编码。

## 5. 服务端汇总

把原始阶段映射为深度、核心、REM、清醒，分别累计对应时长。

总睡眠按深度、核心、REM 相加；清醒单列，卧床也单列，不能混进总睡眠。不要把捷径对所有睡眠样本做的「总和」直接当作 `sleep_hours`；已有分期后，去掉这个混算字段。

睡眠会跨午夜。手机端和接收端须约定同一晚的日期归属及起止范围，覆盖入睡到醒来的记录，并检查是否混入相邻一晚。对账时使用相同范围，不能只把查询窗口不断放宽。

## 6. 安全

配置中仅使用占位符：

```text
WEBHOOK_URL=<用户自己的接收地址>
WEBHOOK_KEY=<用户自己的密钥>
```

真实地址和密钥只在用户自己的手机／服务端配置。禁止提交真实密钥、完整请求地址、健康导出 ZIP、原始健康文件或可识别的连续明细。说明与分享包默认纯文字，不附个人标识、私聊或未脱敏截图。

## 7. 验收与日常使用

选健康 App 中某一晚，对照 Bot 汇总的深度、核心、REM、清醒和总睡眠；卧床单独核对。验收前先确认日期范围和单位一致。

已有一次核对记录的约数：深度约 1 小时 02 分、核心约 3 小时 21 分、REM 约 1 小时 08 分、清醒约 5 分、卧床约 8 小时 31 分。前三项合计约 5 小时 31 分。这组数据仅说明核对方式，复现者应以自己的健康 App 为准。

日常流程：**戴表睡 → 早上打开微信 → Bot 给出总睡眠、各阶段与活动数据的中文小结。** 有连续记录时可对比近几天；小结不作治疗或诊断判断。

作为健康资料库积累记录时，保留数据来源和日期范围，区分原始记录与 Bot 的分析。未戴表或缺少记录的日期标为缺失，不补造数据；历史资料也仅保存在用户自己的私有环境中。

## 8. 暂无快捷指令文件

当前不提供 `.shortcut` 文件，按本说明新建并逐项验收。

## 常见失败

- **大量样本无法共享：** 一次读取上百条时可能触发权限提示，检查第 3 节的设置。
- **「深度睡眠」筛不到：** 捷径对睡眠「值」使用中文过滤可能匹配失败，改为发送原始阶段列表和对应时长，在接收端汇总。
- **时长像是两晚相加：** 检查跨午夜的日期窗口，排除相邻一晚。
- **总睡眠异常偏大：** 检查是否把卧床、清醒和其他睡眠记录一起求和；按第 5 节重新计算。
- **长按方块只能拖动：** 新版快捷指令中可能无法这样复制，同类方块重新搜索添加。
