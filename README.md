# 给 Bot 的执行说明：打开微信 → 捷径 → webhook → 中文健康小结

版本：v3｜2026-10-24｜供 Grok Bot／同类助手读取并带用户操作。

## 1. Bot 先明确任务与完成标准

你的任务是带用户完成每日同步：早上戴表睡醒后打开微信，iPhone「快捷指令」（下称捷径）读取苹果健康数据，POST 到用户自己的 webhook，接收端保存记录，再由 Bot 给出中文小结。微信在这里是触发器；小结默认发到用户与 Bot 的私有会话，不代表能直接发送到微信。

按下面顺序带做，每次给一小段可点击步骤，用户完成后再进入下一段；按钮名称随系统版本不同，以用户屏幕为准。当前没有可导入的 `.shortcut` 文件，需要新建。不要把本文当成已部署证明，也不要只回复“配置成功”。完成必须同时看到：**手机实际触发、接收端实际入库、中文小结实际送达、睡眠数据对账通过。**

先确认三件事：健康 App 已有昨晚睡眠记录；手机时区与接收端约定一致；你的平台确实支持带鉴权的 webhook routine、持久保存和私有消息投递。不支持某项就说清缺哪项，先停在对应环节，不编造 URL、密钥或搭建成功的回执。

## 2. 先建 Bot 侧 webhook routine

### 用户可以直接对 Bot 说

> 帮我建健康 webhook routine，接收 iPhone 快捷指令 POST 的 JSON，用 Authorization: Bearer 校验密钥。按这份说明校验字段，把睡眠阶段列表和对应秒数配对，分别汇总深度、核心、REM、清醒，实际睡眠只算 deep + core + REM，InBed 单列。按我的本地日期更新同一天的记录，不重复累加；生成中文小结，有可比历史再做对比，发到我们约定的私有会话。请给我可复制的 webhook URL 和 Key，并说明小结发到哪里、如何验证成功。真实 Key 只用于我的私有配置，不写入共享文件。

### Bot 的执行清单

- 新建或复用这位用户专属的 routine，确认 HTTPS 接收地址和密钥管理方式。记录用户时区、消息目的地与下文统计口径；URL、Key 通过平台的私有配置界面交付，随后引导用户复制进捷径。
- 先校验 Bearer，再解析 JSON；鉴权失败不写库、不生成健康小结，日志不得记录完整密钥。密钥必须绑定用户，不能让请求体自行指定别人的记录。
- 校验 `date` 为有效的 `yyyy-MM-dd` 日期、`source` 为约定值；有值的活动指标须为合法数值。两条睡眠字符串均为空时记为缺失；否则按逗号或换行拆分、去除首尾空白，逐项配对。有空项、长度不等、负时长或非数字时长就报错，不自行删掉一侧元素凑齐。
- 在接收端识别阶段：`AsleepDeep` → deep，`AsleepCore` → core，`AsleepREM` → REM，`Awake` → awake，`InBed` → 卧床。实际输出若是数字或其他语言，先核对映射再处理；未知阶段标为“待识别”，不猜编码。未分期的 Asleep 不能与已分期睡眠叠加，也不能强分成 deep/core/REM。
- 分别累计秒数：**实际睡眠秒数 = deep + core + REM**；awake、InBed 单列。列表不完整、来源重叠或窗口未核实时，不宣称得到完整的一晚总睡眠。
- 按“用户 + 本地 `date`”做 upsert：首次新增，再次更新；当天活动值是截至本次同步的累计或均值，不能再加到旧值上。保存接收时间、来源、口径和校验状态。空样本或疑似截短的睡眠结果不得覆盖当天已验收的完整睡眠；仍可更新有效的活动指标。
- 同日相同内容重复请求不重复建记录、不反复发相同小结。可在数据变化后更新小结；并发请求也应保持同一天一条记录。
- 只在写库成功后返回明确回执，并投递中文小结；若采用异步处理，先说明“已接收，待处理”，直到写库与消息投递完成才算成功。消息发送失败单独记录并补发，不能靠再次累加数据恢复。

例如可以约定成功响应如下；这是建议的接口契约，Bot 必须落实后才能让用户据此判断，不能假定平台原生返回这些字段：

```json
{"ok":true,"date":"2026-10-24","saved":true,"summary_status":"sent"}
```

## 3. 手机端：按方块顺序新建捷径

打开「快捷指令」App →「快捷指令」页 →「+」→ 命名为 **健康每日同步**。逐个搜索并添加下列操作；每段结束用「设定变量」保存结果，后续选择对应变量，不要误用紧挨着的上一个输出。

### A. 取睡眠样本，生成两条一一对应的列表

1. 添加「查找健康样本」：类型选 **睡眠**，不要选“睡眠变化”；开始日期设为 **最近 1 天**；不要添加“值是深度睡眠”等文字过滤。按开始日期从早到晚排序，关闭条数限制。将结果设为变量 `sleep_samples`。
2. 从同一份 `sleep_samples` 提取每条样本的「值」和「持续时间」。可点样本变量选择属性，或搜索「获取健康样本的详细信息」；如果界面不能直接得到两个列表，就使用「重复每一项」：每次从同一个“重复项目”提取阶段值、时长，分别「添加到变量」`stage_list`、`duration_list`。两个列表每次运行都从空列表开始，不能继承上次结果。
3. 时长统一为 **秒**，保存纯数字。若界面只给开始日期、结束日期，就用「获取日期之间的时间」，计算同一条样本的结束减开始，单位选秒。不要把带“分钟／小时”的显示文本直接当数字；若取到的持续时间为分钟，先乘 60。
4. 对 `stage_list` 用「合并文本」，分隔符选逗号（也可换行），设为 `sleep_stage_values`；对 `duration_list` 用相同分隔符合并，设为 `sleep_stage_durations`。两个列表不可分别排序、独立过滤或删除某一侧的元素。发送前核对条数相等；不等就显示错误并停止捷径。
5. 首次测试可用「快速查看」在手机本地核对一对阶段与秒数；验收后移除会阻塞自动运行的预览。没有睡眠样本时两字段均发空字符串，接收端标记缺失，不将其写成“睡了 0 小时”。

**时间范围约定：** `date` 取运行当天的本地日期，正常晨间同步将昨晚跨午夜的睡眠归到醒来的这一天。“最近 1 天”是滚动窗口，不自动保证只包含昨晚完整睡眠，也可能含午睡、前一晚片段或漏掉较早开始的样本。首次必须和健康 App 核对起止范围；若窗口不符，Bot 带用户在睡眠查询中增加明确的开始／结束日期条件，取已确认的同一晚范围，再重跑。

这份基础 JSON 仅含阶段与时长，接收端无法据此还原每条样本时间或消除重叠。多设备／多 App 的重叠记录应先在手机查询中限定为已核实的睡眠来源；`source: iphone-shortcuts` 只是上传途径，不代表原始健康数据来源。当天晚些时候再次触发，也不能把滚动窗口缩短后的睡眠覆盖完整晨间结果；无法确认时标为待核对，保留已验证记录。

### B. 取今天的活动与心率指标

在睡眠方块后继续添加四段查询。每段都是「查找健康样本」→ 提取样本的数值 →「计算统计数据」→「设定变量」。开始日期均为 **今天**，关闭条数限制。

| 查询类型 | 统计操作 | 保存变量 | 统一单位与口径 |
| --- | --- | --- | --- |
| 步数 | 总和 | `steps` | 步，今天零点到当前 |
| 活动能量 | 总和 | `active_energy_kcal` | kcal，今天零点到当前，不是总能量 |
| 静息心率 | 平均值 | `resting_hr` | 次／分钟，今天可用样本的算术平均 |
| 心率变异性（HRV） | 平均值 | `hrv` | 毫秒（ms），今天可用样本的算术平均 |

如果列表为空，用「如果」分支跳过该项统计，并在最终词典中省略该键；接收端按缺失处理，不用 0 代替没有数据。HRV 与静息心率不得求和。健康样本直接相加不保证等于健康 App 去重后的展示值：若手机和手表同时贡献重叠步数／能量，先核对来源并在查询中限定单一来源，说明统计口径，不能把明显重复的总和验收通过。

### C. 取日期、组词典、发送 POST

1. 添加「当前日期」→「格式化日期」→ 自定格式输入 **`yyyy-MM-dd`**，使用约定的本地时区，设变量 `date`；不要用 `YYYY` 或将日期写死。
2. 添加「词典」，按第 4 节设置键。四个活动指标选数字类型并插入对应变量；日期、两条睡眠列表和 `source` 选文本类型。变量要通过变量选择器插入，不能把变量名当普通文字输入。缺失的活动键不加入词典。**不要添加或发送 `sleep_hours`。**
3. 添加「URL」，填用户自己的 webhook 地址；再添加「获取 URL 内容」，输入选刚才的 URL，展开更多选项，方法改为 **POST**。
4. 请求头添加 `Authorization`，值为 `Bearer YOUR_WEBHOOK_KEY`，用户在自己的手机上替换 Key；`Bearer` 后保留一个空格。另设 `Content-Type: application/json`。
5. 请求体选 **JSON**，让字段来自上一步词典。如果该版本界面只能逐行添加字段，就按词典同名键逐行设置，在值处选择对应变量（也可用「获取词典值」取值）；活动指标保持数字类型。最终发出的是第 4 节的顶层 JSON 对象，不能变成一个名叫 `body` 或 `payload` 的字符串，也不能额外包一层词典。
6. 联调时在末尾添加「快速查看」，查看接收回执；通过后移除预览或改为不阻塞的通知。网络请求结束不等于已入库，按第 2 节约定的回执判断。

Apple 的「获取 URL 内容」在 POST 模式下可配置 JSON 请求体，字段可手动输入或使用变量，参见 [Apple 官方 API 请求说明](https://support.apple.com/zh-cn/guide/shortcuts/apd58d46713f/ios)。

### D. 首次手动运行与授权

点捷径的运行按钮，在系统提示中授予上述健康类型的读取权限，以及向用户自己的接收域名发送数据的权限。若一次共享样本较多被拦截，到 **设置 → 快捷指令 → 高级 → 允许共享大量数据**；某些系统版本需先进入“设置 → App → 快捷指令”，按实际入口查找。

先手动跑通一遍，再建自动化。授权弹窗未处理完时，不能期待后台无人值守运行。

## 4. 完整 JSON 与鉴权示例

以下是纯示意数据，不是用户实测值。示例只有四条阶段记录；实际发送所有已核对样本，不带省略号。

```json
{
  "date": "2026-10-24",
  "steps": 8234,
  "active_energy_kcal": 420,
  "resting_hr": 58,
  "hrv": 42,
  "sleep_stage_values": "AsleepDeep,AsleepCore,AsleepREM,Awake",
  "sleep_stage_durations": "3720,12060,4080,300",
  "source": "iphone-shortcuts"
}
```

```text
URL: https://YOUR_WEBHOOK_URL
Method: POST
Authorization: Bearer YOUR_WEBHOOK_KEY
Content-Type: application/json
```

这里的时长单位固定为秒。接收端应算出深度 1 小时 02 分、核心 3 小时 21 分、REM 1 小时 08 分、清醒 5 分；实际睡眠是 **5 小时 31 分**。清醒不计入实际睡眠；这组示例没有 InBed，不能反推出卧床时长。若使用换行分隔，由 JSON 序列化处理为 `\n`，不要手拼非法 JSON。

## 5. 自动化：打开微信时运行

1. 打开「快捷指令」→「自动化」→「+」→「创建个人自动化」（有些版本直接选触发条件）。
2. 选择「App」→ 选择 **微信** → 勾选 **已打开／打开时**，不要选“已关闭”。
3. 选择 **立即运行**；若页面使用旧版措辞，则关闭 **运行前询问**，确认“不询问”。
4. 选择运行「健康每日同步」；若进入空白操作页，就添加「运行快捷指令」方块，指定这条捷径，再保存。
5. 确认自动化已启用。回到主屏幕后打开微信，观察接收记录和 Bot 小结是否出现。

App 触发支持不询问直接运行，参见 [Apple 官方个人自动化说明](https://support.apple.com/zh-cn/guide/shortcuts/apd602971e63/ios)。这里按 Cooper 提供的方案使用打开微信触发，因为锁屏定时读取健康数据不可靠；不要把链路改成仅靠锁屏定时执行。

**“每日同步”不等于每天只触发一次。** 每次打开微信都可能触发，因此依靠第 2 节的同日 upsert 与相同内容去重；未打开微信、手机离线或手表记录尚未同步时，不保证当天已有有效记录。晨间活动数据只代表今天截至当时，不能说成昨天全天活动量。

## 6. Bot 的中文小结怎么写

小结应包含日期、最新接收时间、已核对的睡眠范围、实际睡眠与各阶段、今天截至同步时的活动／心率数据，以及缺失或待核对项。下面只展示格式，数值来自第 4 节示例：

> 10 月 24 日健康同步：本次示例睡眠合计 5 小时 31 分，其中深度 1 小时 02 分、核心 3 小时 21 分、REM 1 小时 08 分，清醒另计 5 分；未提供卧床记录。今天截至本次同步，步数 8,234，活动能量 420 kcal，静息心率样本均值 58 次／分，HRV 样本均值 42 ms。目前没有可比历史，暂不做趋势比较。

实际发送时使用真实接收值和核验状态，不照抄示例。只在已有同口径记录时对比前一晚或近期有效晚间均值，说明比较天数；活动比较还需匹配时段，不能拿今天早上的累计值对比昨天全天。缺数据写“缺失”，阶段不明写“待识别”；不根据一次读数作诊断或治疗判断。

## 7. 验收：Bot 逐项核实，不能只看 HTTP 成功

- [ ] **手动通路：** 用户解锁手机手动运行捷径，授权完成；接收端能看到正确用户、日期、字段与单位，回执确认写入成功。
- [ ] **解析测试：** 用第 4 节示意 JSON 在测试记录中验证合计为 5 小时 31 分，清醒单列；再测试加入 InBed 不增加实际睡眠、两列表不等长会被拒绝。测试数据与正式记录隔离。
- [ ] **真实对账：** 选用户健康 App 中同一晚，对照 deep、core、REM、awake 及可用的 InBed；确认秒与分钟换算、跨夜归属、来源和起止范围。解释显示舍入差异，不能靠调数字凑齐。
- [ ] **鉴权测试：** 用占位假 Key 的测试请求被拒绝且不写库；正常 Key 只在私有环境配置，不展示到截图或公共日志。
- [ ] **自动触发：** 退出到主屏幕再打开微信，无“运行前询问”；接收端出现本次时间的记录。不能仅凭自动化开关已打开判定成功。
- [ ] **中文小结送达：** 约定的 Bot 私有会话确实出现小结，数值与入库记录一致。HTTP 已接收但消息没到，仍未完成整条链路。
- [ ] **重复与缺失：** 再次打开微信，同日仍只有一条记录、活动未被累加、相同内容不刷屏；缺失字段不变成 0，截短／空睡眠不覆盖已验证的完整睡眠。

验收结束，Bot 给出“已通过哪些项、尚缺哪项、下一步点哪里”的简短回执。仅当以上必要检查完成后，才告诉用户每日链路已接通。

## 8. 常见失败与下一步

| 现象 | Bot 带用户排查 |
| --- | --- |
| Bot 无法提供真实 webhook | 先确认平台支持接收请求、鉴权、保存与消息投递；缺能力就说明阻塞点，不拿普通聊天链接冒充 webhook。 |
| 打开微信没反应 | 检查选中微信、触发为“已打开”、已启用、立即运行／关闭询问、运行的捷径名称正确；先手动运行定位是捷径还是触发问题。 |
| 有权限提示、样本为空 | 先解锁手动运行并授权；确认健康 App 本身已有记录、手表同步完成，再检查日期条件；不要把无权限视为没睡觉。 |
| 大量样本无法共享 | 检查“允许共享大量数据”，在本机处理授权提示后重试。 |
| “深度睡眠”筛不到 | 类型改为“睡眠”，移除“值是深度睡眠”文字过滤，发送原始阶段值，由接收端映射。 |
| 两列表不等长／时长大 60 倍 | 检查两列表是否来自同批同序样本；统一秒数，核对是否把分钟当秒或重复乘 60；修复前停止汇总。 |
| 睡眠变成两晚、总数偏大或越同步越少 | 核对滚动窗口、样本来源、重叠与跨午夜边界；排除 InBed／Awake／未分期记录重复计入；不能用不完整的新窗口覆盖完整旧记录。 |
| 步数／能量比健康 App 高 | 检查是否把手机和手表重叠记录直接相加；限定经核实的来源并重新对账，不声称原始样本总和自动完成了去重。 |
| 401／403 | 检查 URL 是否属于当前 routine、Authorization 键名、`Bearer` 后空格和 Key 是否过期；用户在本机检查，勿回传真实 Key。具体错误含义以接收端回执为准。 |
| 400／422、提示 JSON 错误 | 检查字段名、数字类型、缺失键、列表长度、是否带省略号或套了 `payload`；正文必须是 JSON 对象。 |
| 404／405、超时或服务端错误 | 检查完整 URL、POST 方法、网络和 routine 是否启用；有限重试，不持续刷请求；重试仍按同日更新，不能重复累加。 |
| HTTP 成功但无小结 | 查是否只是排队接收、是否已保存、消息目的地是否正确及投递状态；修复消息投递，不把“接收到请求”当作消息送达。 |
| 长按方块只会拖动 | 不继续尝试长按复制；重新搜索添加同类操作，逐项选回正确变量。 |

## 9. 私有配置与可选进阶

本文、共享包和仓库只保留占位符。真实 webhook 地址与 Key 只进入用户自己的私有配置；不提交真实密钥、带密钥的完整请求、个人健康明细、可识别截图或敏感日志。调试只索取脱敏错误与必要字段结构；若密钥泄露，先在接收端作废并更换，再更新手机配置。

可选进阶：每日同步验收后，再按用户需要另行安排历史健康 ZIP 导入。
